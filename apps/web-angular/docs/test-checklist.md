# Angular 專案測試案例與 QA 真實情境檢核表 (Checklist)

本文件參考 Next.js 專案的現有測試設計，並從 QA（品質保證）角度出發，列出 Angular 前端專案應覆蓋的完整測試項目與真實情境。

## 1. 會員註冊與登入模組 (Auth Module)

### 1.1 會員註冊 (Register)
* [ ] **基本註冊流程**：輸入正確的 Email、顯示名稱、密碼，點擊註冊後能成功導向 `/login`。
* [ ] **欄位格式校驗 (VALIDATION_ERROR)**：Email 格式不符、密碼長度不足、或顯示名稱為空時，前端需進行即時提示，若 API 回傳 `422` 錯誤，需顯示「請確認 email、顯示名稱與密碼格式。」。
* [ ] **Email 重複使用 (EMAIL_ALREADY_USED)**：輸入已被註冊的 Email，API 回傳 `409` 時，顯示「此 email 已被使用。」。
* [ ] **請求防重複送出**：點擊註冊按鈕後，按鈕應呈現「註冊中...」並處於停用 (disabled) 狀態，避免使用者因多次點擊發送重複請求。
* [ ] **錯誤狀態重設**：若前一次註冊失敗顯示錯誤訊息，當使用者修改欄位並再次點擊註冊時，應先清除舊的錯誤訊息。
* [ ] **系統/網路異常處理**：網路中斷或 API 伺服器無回應時，應正確擷取錯誤並顯示通用提示「系統暫時無法處理請求。」。

### 1.2 會員登入 (Login)
* [ ] **成功登入流程**：輸入正確帳密，點擊登入後成功導向 `/my/bookings`，並重新整理 (refresh) 使用者狀態。
* [ ] **帳密錯誤處理 (INVALID_CREDENTIALS)**：輸入錯誤密碼或未註冊 Email，API 回傳 `401` 時，顯示「帳號或密碼錯誤。」。
* [ ] **帳號停用處理 (USER_DISABLED)**：登入已被停用的帳號，API 回傳 `403` 時，顯示「此帳號已停用。」。
* [ ] **登入頻率限制 (RATE_LIMITED)**：短時間內多次登入失敗，API 回傳 `429` 時，顯示專用提示「登入太頻繁，請稍後再試。」。
* [ ] **請求防重複送出**：點擊登入按鈕後，按鈕應呈現「登入中...」並停用。
* [ ] **錯誤狀態重設**：再次點擊登入時，應先清除之前的錯誤訊息。
* [ ] **網路異常處理**：網路錯誤或伺服器異常時，顯示「系統暫時無法處理請求。」。

### 1.3 管理員登入 (Admin Login)
* [ ] **管理員登入流程**：成功登入後，呼叫 `/api/admin/auth/login` 端點並正確導向後台預約管理頁面 `/admin/bookings`。
* [ ] **非管理員權限處理 (FORBIDDEN)**：一般會員嘗試登入後台，API 回傳 `403` 時，顯示「此帳號無後台管理權限。」，且不應引發前台會員登出的副作用。

## 2. 公開服務與時段瀏覽模組 (Public Browse & Service Detail)

### 2.1 服務列表頁 (Services List)
* [ ] **狀態顯示過濾**：
  * 「啟用 (Active)」與「停用 (Inactive)」狀態的服務應顯示在列表上。
  * 「隱藏 (Hidden)」狀態的服務不應呈現在公開列表中。
* [ ] **停用服務標記**：Inactive 狀態的服務卡片上應清晰標示「暫停預約」。

### 2.2 服務詳情頁 (Service Detail)
* [ ] **時段顯示規則**：
  * 僅能顯示狀態為 `available` 的可用時段。
  * 必須符合「僅能預約 1 小時後」的安全規則（已小於 1 小時或過去的時段不可顯示）。
* [ ] **停用服務詳情頁**：直接以 URL 開啟 Inactive 服務詳情頁時，應可正常瀏覽服務內容，但須顯示提示「此服務目前暫停預約，仍可查看服務內容。」，且畫面上不應出現任何預約時段與預約按鈕。
* [ ] **隱藏服務防護**：直接以 URL 開啟 Hidden 服務詳情頁時，系統應回傳 `404` 頁面（找不到頁面）。
* [ ] **不存在的服務處理**：輸入無效的 Service ID 網址時，應正常導向 `404` 頁面。
* [ ] **無時段 Empty State**：當 Active 服務目前沒有任何可用時段時，時段區域應顯示 Empty State 文案「目前沒有可預約時段，請稍後再回來查看。」。

## 3. 預約操作模組 (Booking Actions)

* [ ] **成功預約流程**：
  * 點擊「預約」按鈕後，按鈕狀態應更新為「建立中...」並停用。
  * 預約成功後，導向該預約的詳情頁，並在網址帶入 `?promptCalendar=1` 參數。
* [ ] **未登入引導 (UNAUTHENTICATED)**：未登入狀態點擊預約，應引導至登入頁，並在網址帶上當前服務詳情頁的返回參數，例如 `/login?redirect=/services/:serviceId`。
* [ ] **時段已被搶佔 (BOOKING_SLOT_UNAVAILABLE)**：若在選取時段後，該時段被他人捷足先登，API 回傳 `409` 時，前端顯示「此時段目前不可預約，請重新整理後選擇其他時段。」，並主動刷新當前頁面資訊。
* [ ] **預約時段過近 (BOOKING_TOO_SOON)**：預約距離現在小於 1 小時的時段，API 回傳 `422` 時，顯示「只能預約 1 小時後開始的時段。」。
* [ ] **重複預約防範 (BOOKING_DUPLICATED)**：同一會員重複預約相同時段，API 回傳 `409` 時，顯示「你已預約過此時段。」。
* [ ] **頻率限制與網路錯誤**：觸發 `RATE_LIMITED` 顯示「操作太頻繁，請稍後再試。」；網路錯誤顯示「系統暫時無法處理請求。」。
* [ ] **錯誤清除機制**：修正錯誤重新點擊預約時，舊的錯誤訊息應被自動清除。

## 4. 會員個人預約管理 (My Bookings)

### 4.1 預約列表 (Bookings List)
* [ ] **列表渲染**：正確展示所有與登入會員相關的預約，包含服務名稱、預約時間、預約狀態（如已確認、已取消）。

### 4.2 預約詳情頁 (Booking Detail)
* [ ] **加入日曆功能**：詳情頁面常駐「加入日曆」按鈕，點擊後觸發 `.ics` 檔案下載，方便使用者匯入行事曆。
* [ ] **首度預約完成提示 (Prompt Calendar)**：
  * 若網址攜帶 `?promptCalendar=1` 參數，頁面載入時需自動彈出「是否加入日曆？」的對話框。
  * 對話框彈出後，應立即使用 Router 將網址參數清除（改為 `/my/bookings/:bookingId`），避免使用者手動點選瀏覽器重新整理時，對話框重複彈出。
* [ ] **當日天氣資訊預報 (Weather Widget)**：
  * **載入狀態**：天氣資料尚未回傳前，顯示「正在載入天氣...」。
  * **成功載入**：正確解析 API 資料，顯示該預約日期當天的天氣描述（如：晴、雨）、平均溫度、以及預約的地點。
  * **超出預報範圍 (3天限制)**：若 API 因日期超出近 3 日範圍而回傳 `null`，天氣區塊應顯示「目前僅提供近 3 日天氣預報，請出發前再查看。」。
  * **天氣 API 故障容錯 (502 / WEATHER_UPSTREAM_ERROR)**：若天氣服務因任何原因失敗，天氣區塊應顯示「暫時無法取得天氣，請稍後再試。」，**但不應阻礙詳情頁面其他基本預約資料（服務資訊、加入日曆等）的正常顯示**。

## 5. 後台預約管理模組 (Admin Dashboard Bookings)

### 5.1 預約日曆與列表 (Bookings Calendar)
* [ ] **分頁過濾功能**：
  * 預約清單應分為「一般」與「已取消」兩個 Tab。
  * 「一般」分頁應包含 `confirmed`、`pending` 等非取消狀態的預約。
  * 「已取消」分頁則只顯示 `cancelled` 的預約單。
* [ ] **月份切換**：點擊日曆的「上個月 / 下個月」時，應能正常切換，並同步更新網址的 query 參數（如 `?month=2026-07`），使重新整理後仍停留在該月份。

### 5.2 建立預約對話框 (Create Booking Dialog)
* [ ] **會員查詢功能**：輸入會員 Email 並點擊「查詢」時，應呼叫 API 驗證並於下方顯示該會員的顯示名稱（如：測試用戶）。
* [ ] **連動選取與提交**：選取會員後，需可選擇服務、日期與時段。確認所有必填欄位填寫完畢後，「確認建立」按鈕才可啟用。

### 5.3 編輯與取消預約對話框 (Edit & Cancel Booking Dialog)
* [ ] **改期功能**：編輯對話框應能載入目前服務的其他可用時段，點擊新時段並送出後，正確更新預約時段。
* [ ] **取消預約**：取消預約對話框必須提供「取消原因」輸入欄位。填寫原因點擊提交後，應將原因傳送給 API 儲存，並順利將預約狀態更新為已取消。

## 6. QA 真實情境擴充 (QA Real-World Scenarios)

### 6.1 網路不穩定與邊緣案例 (Network & Edge Conditions)
* [ ] **極端延遲與連續點擊防護 (Race Condition)**：
  * 在慢速網路 (Slow 3G) 下，測試「預約」、「登入」、「註冊」按鈕是否確實只送出一次請求。
  * 頻繁點擊分頁切換時，前端是否會因非同步 API 回傳順序不一（Race Condition）而顯示錯誤的月份或時段資料（應以最後一次請求為準或阻斷前次請求）。
* [ ] **完全斷網環境 (Offline)**：在離線狀態下，點擊各操作按鈕，應有顯著的斷網錯誤提示，而非頁面卡死或控制台噴錯。

### 6.2 時間與時區相容性 (Time & Timezone Boundaries)
* [ ] **跨時區預約時間正確性**：若使用者系統時區非台灣時間（例如東京 UTC+9、美東 UTC-5），確認預約顯示的時間是否正確轉換，不應因為時區偏移而發生顯示日期或小時錯誤。
* [ ] **時間邊界臨界點**：
  * 測試「只能預約 1 小時後」的臨界時間。例如目前台灣時間為 12:00:00，時段 13:00:00 應為可預約邊界，而 12:59:59 的時段則應不予顯示或在送出時被阻擋。
  * 跨月、跨年的時間點，確認日曆換月顯示與 API parameters 的年份計算是否正確。

### 6.3 系統安全與存取控制 (Security & Route Guards)
* [ ] **越權存取阻擋 (IDOR - Insecure Direct Object Reference)**：
  * 登入會員 A 帳號後，直接以網址輸入會員 B 的預約詳情頁 URL（`/my/bookings/booking-B-id`）。預期應跳轉回首頁/列表，或顯示權限不足，絕不可展示會員 B 的預約內容與天氣資訊。
* [ ] **登入過期處理 (Session Expiry)**：
  * 開啟預約詳情頁，手動清除 LocalStorage/Cookie 的 Token 模擬過期狀態，接著點選「加入日曆」或操作選單。確認發送 API 回傳 `401` 時，系統能平滑導回登入頁，且 URL 帶有當前頁面的 redirect path。
* [ ] **路徑守衛 (Route Guard) 穿透測試**：
  * 未登入狀態直接輸入 `/admin/bookings`，確認是否會被 Route Guard 擋下並強行重導向至後台登入頁。
  * 一般會員權限登入後，嘗試直接輸入 `/admin/bookings`，確認是否會被擋下並提示權限不足。

### 6.4 響應式佈局與裝置體驗 (Responsive & UI/UX)
* [ ] **日曆於行動裝置之可用性**：在小螢幕（如 iPhone SE 等 375px 寬度）下，日曆格線不應重疊擠壓，且日期數字與預約點標記需易於手指點擊。
* [ ] **日曆加入按鈕在行動裝置之行為**：測試在 iOS Safari 與 Android Chrome 下，點擊「加入日曆」下載 `.ics` 時，能否被系統預設的日曆應用程式（如 Apple Calendar、Google Calendar）正常開啟並解析。
